# 2026-08-19

## Remote-control's flaky restarts root-caused and hardened

Been having to restart Claude Code's remote-control connection by hand fairly often to keep using it from mobile. Dug into the logs and it wasn't a real conflict — periodic network blips (DNS lookups failing, TLS certificate checks failing, timeouts) were breaking the connection to the API, and sometimes the process kept running anyway, just stuck in its own reconnect loop with nothing catching it. Taught the existing watchdog to actually check reachability instead of only checking whether the process was alive, debounced so a single bad check doesn't trigger anything (most blips clear themselves within a couple minutes on their own) — only two failed checks in a row force a restart, with a cooldown afterward so a genuine longer outage doesn't get hit with a pointless restart every couple minutes. Caught a real bug mid-build: the first version of the reachability check flagged a normal, harmless response from the API as a failure, which would have force-restarted a perfectly healthy connection constantly — fixed and verified working before it went live. Also added log rotation to the connection's log file, which had grown unbounded to over 150MB with nothing ever trimming it.

## A way to browse the logs from the homepage, now with tiny AI summaries

Added a small section to the homepage, above the main service grid, linking into both log repos: the most recent and a random entry from the daily logs, plus the same pair from the research logs — four cards total, each showing a date, a headline, and now a one-sentence AI-generated summary from the local Ollama instance. Since Ollama only runs on the server itself and a cold model load takes 10-30 seconds, generating those summaries live on every visit wasn't workable — settled on a small background job that reads both log repos directly, generates summaries, and caches them, so the homepage always serves instantly. The most-recent cards update automatically whenever a new entry gets pushed; the random picks are a stable "pick of the day" rather than reshuffling on every visit.

## A new place to share troubleshooting scripts

Stood up a small new tool for one-off troubleshooting scripts (mostly PowerShell): talk through a problem, a script comes out of it, and it publishes as a shareable card — a title, a short description of the problem and what the script does, and the script itself, syntax-highlighted. The point is being able to open that link on whatever machine actually needs the fix, including a coworker's, and just copy it over — no login involved anywhere, since a login cookie has no business landing on someone else's computer, and publishing only ever happens from a direct conversation, never over the open web. Hit one real gotcha wiring up the new address for it: pointing the domain at the new tunnel by name silently routed to a different, already-existing tunnel instead, with no error and the tool's own success message reporting the wrong tunnel's ID — caught by checking the tunnel's actual info rather than trusting the create output, fixed by pointing at its real ID instead of its name. Later added one exception: deleting a case straight from the site itself, gated behind the usual shared PIN and scoped to just that one button — browsing, opening, and copying a case all stay exactly as open as before.

## A bootstrap prompt for standing up a second machine

Wrote a companion to the existing disaster-recovery document: a single markdown prompt that acts as the install script for standing up a second machine as an additional server location, building just a PIN-gated SSH terminal in the existing pattern, not the whole stack. Landed on writing it as engineered context rather than a source dump — real requirements and hard-won gotchas spelled out so a fresh Claude session can write the code itself, instead of just pasting in and executing the working implementation verbatim.

## SODIMM-to-DIMM adapter test: failed to POST

Ran the higher-risk mixed-RAM test that's been queued since the adapter cards arrived — two native desktop sticks plus two laptop-style sticks through SODIMM-to-DIMM adapters, all four slots populated at once. The board failed to POST: no display, no beep, and the onboard debug LEDs weren't legible on this case/board combo, so no clean read on which stage it stuck at. Reverted immediately to the native two-stick configuration and confirmed a normal boot afterward. This was flagged going in as the highest-risk version of the idea, so the result wasn't a surprise, and it's written up properly in the research log; the more modest fallback test — just the two adapter sticks alone, no mixing — is still an open next step.
