# 2026-08-29

## Fixed two bugs in the mobile chat frontend

Chased down two recurring issues reported on the phone-chat frontend: replies
sometimes not showing up on screen, and an occasional JSON-length error that
killed a turn outright. Root causes turned out to be unrelated to each other.

The JSON error was a hardcoded 1MB cap on how big a single message from the
underlying Claude Code session's transport is allowed to be before it's
treated as corrupt and the turn is aborted. The underlying Claude Code
session routinely produces tool output (reading a large file, a verbose
command output, a big web fetch) well over 1MB as a single message, so it
was tripping constantly — confirmed straight from the app's log, which had
several "exceeded maximum buffer size" failures logged. Raised the cap to
20MB so normal-sized tool output stops triggering it, while a truly
oversized single message still fails loudly instead of the process eating
unbounded memory.

The missing-messages bug was a mobile-specific gap in how the chat reconnects
its live event stream. There was already a fix from a few days back that
re-syncs the chat from its saved history whenever the live connection
reopens — but that only runs if the browser actually notices the old
connection died and fires its "reconnected" event. Backgrounding the app on
a phone (screen lock, switching away) freezes its JS entirely, and the
connection can go stale without ever notifying the frozen page, so the
existing re-sync code just never ran. Added a listener that forces a full
reconnect whenever the app becomes visible again, which guarantees the
existing re-sync logic actually fires every time, not just when the browser
happens to detect the drop on its own.

## A third bug in the same app: a multiple-choice question was never actually being asked

Also ran down a report that a clarifying question with a few tappable
options — something the assistant can ask mid-conversation — would
sometimes just vanish, with the turn moving on as if it had been answered.
Root cause was a "full auto" toggle the chat app offers per conversation,
meant to skip the approve/deny card in front of an action like a file edit
or a command so it can just run unattended. That toggle was treating a
question the same way: auto-approving it by handing the question straight
back to the assistant as if it were its own answer. Fine for a real action
with a real effect to skip confirming, meaningless for a question, since
the only legitimate answer is one a person actually picks. Carved that one
case out of full-auto permanently — it now always waits for a real tap —
and replaced what used to be a bare approve/deny card for it with actual
answer buttons. Getting the answer back to the assistant in a form it would
actually recognize took a bit of digging — a first attempt was silently
rejected, and the right shape only turned up in the CLI's own bundled type
definitions. Verified against a disposable test conversation, torn down
afterward, before touching anything real.
