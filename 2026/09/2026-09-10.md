# 2026-09-10

## Intent / Shape / Proof: a compressed prompt model

Worked out a condensed, three-part model for a single natural-language coding
prompt, as a lighter alternative to the existing heavier default — ideate with
the AI, let it draft a full spec sheet, use the spec sheet as the build prompt
— which is genuinely useful for large or ambiguous builds but overkill for a
smaller, well-understood one. The three parts: **Intent** (the outcome plus the
context it has to sit inside — why/where), **Shape** (the interface, an
explicit scope boundary, and the edge cases that matter — what, exactly), and
**Proof** (a concrete verification step — how it'll actually get checked).
Confirmed as the standing default for coding prompts going forward, and
explicitly not scoped to a first build only — the same three questions apply
to adding a feature, removing one, or iterating on something that already
exists.

The deeper motivation behind wanting this: prompt engineering and context
engineering aren't competing practices, they're different layers. Context
engineering (an AI drafting its own spec from a conversation) is genuinely
useful but hands the framing work to the AI by default. Something still has to
generate that context in the first place, and doing that well — especially
iteratively, across rounds rather than accepting a first draft — is what keeps
the framing decision with the developer instead of delegating it away. Since
the real power turned out to be in the iteration rather than getting lucky on
one pass, that lands on prompt engineering being at least as important as
context engineering, not a lesser layer underneath it.

## First trial: a Steam Deck controller tester, shipped as a one-shot

Ran the model against a real request the same day: build a browser tool that
visualizes a Steam Deck's (or any gamepad's) button and stick input live, for
spotting stick drift and checking button responsiveness. All three parts
translated directly into build decisions with zero clarifying back-and-forth —
Intent settled the mechanism (the browser's Gamepad API, polled every frame,
since the spec has no press/release events), and Shape settled the whole
visual language in one line (white outline on dark grey, buttons fill white on
press, a dot tracks stick movement) while also surfacing the one real gap
Shape couldn't resolve on its own: the standard Gamepad API mapping has no
defined slot for a Steam Deck's trackpads or back-grip buttons, so those got
routed to a generic raw-readout panel instead of a guessed position on the
diagram.

The actual hardware test came back negative — it doesn't work correctly on a
real Steam Deck. Decided not to chase the bug down. The whole point of a
one-shot trial is showing what a single unrefined prompt actually gets you,
so the build was left exactly as it came out, and the page itself now says so
directly — the original prompt and the build's own pre-test caveat about that
mapping gap are posted on it, so a visitor sees a known limit of one pass, not
an unexplained failure. The real finding for the model: Intent and Shape
closed off the guesswork cleanly, but Proof on a one-shot can name a check
without being able to act on what it reveals — closing that loop (test, fix,
re-check) is iteration by definition, which a single prompt structurally can't
include. Separately, revisiting it prompted the realization that most of the
existing services here were already built this same way, loosely and without
a name for it, through iterative prompting rather than a single pass.

## Institutional backing: a mixed result

Looked into whether anything like this already has real backing outside of
today's ideation. Closest matches: behavior-driven development's
Given-When-Then structure (decades old, maps closely to Proof), and the
2025-2026 rise of "spec-driven development" tooling, which treats a written
spec as the primary artifact and code as a regenerable output of it — real
validation for settling intent and shape before code, though that tooling is
built around the heavier spec-sheet workflow, not today's compressed
single-prompt version. The honest counterpoint: current industry framing
leans the opposite direction from the "at least as important" claim above —
context engineering is being called the more load-bearing skill right now,
with prompt engineering treated as one slice of it rather than a peer
discipline. One benchmark finding cut back the other way, though: an agent
given a small, targeted slice of context outperformed one given a much larger
dump of it, which is closer to a clarity-over-volume instinct than a
more-context-is-always-better one.

## Master prompts vs. showcasing workflow

A related distinction surfaced while comparing this to the existing showcase
format used elsewhere: a showcase's reusable "master prompt" is normally
generated by the AI after a build is already finished, which makes it a
reproducibility artifact — closer to an installer script for an agent — not
an actual demonstration of the prompting that happened. Posting the real,
verbatim original prompt on the controller-tester page (typos included, not
cleaned up after the fact) turned out to already be the right instinct for
showing process rather than product — landed as something worth naming on
purpose going forward, not repeating by accident.

## Coworker idea: a "LeetCode for prompt engineering"

Talked through a practice-site concept with a coworker: give someone a coding
problem, have them submit a prompt instead of code, ideally with iteration
built into the loop. The hard problem it runs into that a normal coding
practice site never had to solve: grading requires actually running the
submission through an agent to get code out before anything can be tested,
which means real per-submission cost and non-determinism where a code judge
just executes for free and deterministically.

The design direction that emerged sidesteps that instead of solving it: no
algorithmic score at all. A profile shows a random sample from a *recent*
window of solved problems, not a lifetime-fixed set, specifically so a handful
of problems solved once and polished can't be presented as someone's entire
track record — the profile just goes stale and visibly inactive instead,
same tell as an abandoned code-hosting profile. Paired with an activity
calendar (a per-day heatmap of problems solved), that was judged sufficient on
its own; a richer per-problem view showing the actual iteration trail was
proposed and then deliberately cut to keep the whole thing deterministic and
cheap to run — the calendar alone does most of the same job for far less
machinery.

Got far enough to settle a working name for the eventual subdomain and an
access model — invite-gated rather than open public signup, with its own
distinct access code rather than the one shared elsewhere, since real accounts
still get created behind it — plus a recommended first version with no
agent-execution grading at all, just capturing and displaying what gets
submitted. Decided to leave it there for now rather than start building. Not
abandoned, just not today.

## Daily-log capture: a consistency gap, caught and fixed

Found a real gap in how today's own capture rule was being followed: the
"log automatically as it happens" instruction was only getting re-checked at
moments that felt like natural pauses, not on every turn, so a conclusion
reached mid-conversation didn't make it into the draft until it was pointed
out directly. The rule itself wasn't wrong — the miss was in applying it
consistently through a long, fast back-and-forth. Filed as feedback, and
picked back up mid-session with a deliberate audit against the actual
conversation, which caught two more sections that had been pushed elsewhere
but never made it into this file. Adopted a light safety net going forward —
an occasional reminder — on top of, not instead of, actually running the
check every turn.
