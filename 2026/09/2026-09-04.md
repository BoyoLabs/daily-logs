# 2026-09-04

## From monochrome grey to amber phosphor

The mobile chat frontend's monochrome grey theme, set only the day before,
turned out to read as an old black-and-white movie rather than a terminal.
Greyscale had stripped out the functional color that makes a shell session look
like one, and underneath the surface details the layout was still app-shaped.
The reskin moved it to the amber phosphor palette the PIN screen already used,
so the two screens stop disagreeing halfway through a login.

The structural changes mattered more than the palette. Three tiers of panel
background collapsed into a single terminal background. The left/right chat
bubbles became a full-width scrollback — a prompt glyph and a left rule for
typed input, plain indented output for replies. The settings toolbar moved below
the message list and became a status line in the style of tmux or vim. Every
button press became inverse video instead of a lighter fill. Scanlines and text
glow were deliberately skipped in favor of a flat modern terminal look, on the
same legibility reasoning that de-glowed the battlestation theme months earlier.

Previewing the whole thing headless at phone width against a throwaway mock API,
rather than the live app, caught two real defects before they shipped: tool names
wrapping one character at a time in the collapsed tool-call line, and multi-line
blank craters above and below every fenced code block.

## Making replies look like output instead of chat

Three follow-on complaints after the amber theme landed were all versions of the
same objection — the app still framed the model's replies as chat content rather
than terminal output.

The fix was a highlighter that colors the machine-shaped parts of a reply using
the exact token colors the code blocks already use, so green means "string"
whether it appears in Python or in a sentence about Python, while narration stays
plain. Tuning that pattern was most of the work. Single quotes had to be dropped
because contractions were reading as strings. Flags and absolute paths needed a
guard so "well-known," "and/or" and "24/7" stopped lighting up. Bare numbers came
out entirely, so dates and list numbering don't strobe.

Code blocks lost their frame and became a gutter rule under a labelled divider,
keeping the copy button that was the box's only real justification. The biggest
change was to tool calls: instead of collapsing into a box holding a dump of the
raw tool input, they now render inline the way the terminal does — a trimmed diff
for edits, a command line for shell calls, and the result hung off the same
connector glyph the CLI uses, all capped with a tap-to-expand so a single file
read can't flood the screen. The approval prompt for an edit shows that diff too,
which is the one place it genuinely matters, since that's where the decision
actually gets made.

## Resuming a past session from the phone

The chat frontend could always continue a conversation it had started itself — it
keeps the session id it gets back and hands it to the next turn — but it had no
way to pick up a session begun anywhere else on the box. Typing the CLI's resume
command into the chat just sends it as a literal message, because the real one is
an arrow-key terminal picker that needs a TTY the web transport doesn't have.

The agent SDK turns out to expose a plain function that reads the session files
off disk and returns ids, titles and timestamps with no TTY involved, which made
the fix small and entirely additive: two new endpoints — list what's resumable,
and mint a chat bound to one of them — plus a button on the main screen opening a
full-screen filterable picker. None of the streaming or model plumbing changed;
picking a session just pre-fills the id the existing resume path was already
reading. The rows show a session id prefix and transcript size, which matters
more than expected, since a lot of sessions open with the same one-word prompt
and the id is the only thing telling them apart.

First real use turned up the obvious hole. Picking a past chat resumed it
correctly, but opened a blank pane: the frontend draws a conversation only from
its own record of it, and had none for a session it never watched. The context
was loaded and the screen was empty — the worst possible pairing, since there's
no way to tell a working resume from a broken one.

The second pass added a translator from the CLI's own on-disk session file into
the frontend's event vocabulary, run once at the moment a session is picked, so
a resumed chat is afterward just a chat that already has history in it. Most of
that work was deciding what *not* to import. Subagent traffic, the synthetic
turns the CLI writes for its own bookkeeping, and thinking blocks that carry a
signature but no text would all have rendered as noise nobody wrote or saw.
History is bookended with dividers, and the closing one doubles as the signal
that nothing is mid-turn — without it, the composer sat disabled on every resumed
chat, resumable but not typeable.

## A ticket sweep turns up a self-inflicted false alarm

A pass over the open items on the ticket dashboard turned up nothing on fire,
but one item stood out: a bug where the dashboard's own tunnel-restart logic
kills the live tunnel process before confirming its replacement actually came
up, so a failure partway through the relaunch — as opposed to the ordinary
brief gap any restart causes — can leave a service silently dark instead of
just blipping. That bug already caused a real outage for a service that has
since been decommissioned, but the restart code itself is shared by every
other tunneled service, so the risk is still live.

Checking whether an existing watchdog already covered this case produced a
wrong answer, entirely self-inflicted. A watchdog built months earlier was
meant to catch exactly this — a dead tunnel process — and bring it back
within a couple of minutes without waiting for a full reboot. The first check
said its schedule had vanished entirely, which was alarming, since the script
on disk was still complete and correct. That conclusion turned out to be
wrong: the session doing the checking runs under a different account than the
one these jobs actually run under, and a bare schedule-listing command
defaults to the caller's own schedule rather than the one that mattered, so
every verification step quietly checked the wrong owner's list the whole
time. The attempted fix then compounded it, writing a duplicate entry back
into that same wrong list instead of the right one. Live impact was zero —
nothing died in the roughly twenty minutes before this got caught, confirmed
by checking process and log ownership directly — but it was a live
demonstration of the same regular-user-vs-root ownership trap that's bitten
this setup before. Cleanup: removed the wrongly placed entry, de-duplicated
the correct list back to one line, and corrected the ticket record with what
actually happened rather than leaving the wrong story standing.

## A stated fact heard as reassurance instead of a lead

Picking apart that false alarm afterward turned up something worth keeping on
its own, separate from the mechanical root cause. Partway through the
investigation, it had been mentioned in passing that this batch of scheduled
jobs runs under one particular account rather than the other — offered as
routine background, not as a correction or a complaint. The next move was to
go check other places the entry could theoretically live, and never to check
under the specific account that had just been named. In hindsight, that
sentence was the single most direct pointer to where the real answer was
sitting, and it got processed as ambient color instead of a lead worth
running down. It's a different failure shape than the mechanical one — not a
wrong command, but a wrong weighting of a true, freely given fact. Worth
watching for again: a plainly stated fact about how a system works, dropped
into conversation with no urgency attached, can still be the whole answer.
