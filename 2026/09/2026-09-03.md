# 2026-09-03

## The mobile chat frontend gets restyled as a terminal session

Reworked the mobile Claude Code chat app's visual theme so it reads as an actual
terminal session rather than a chat-bubble app. Square-cornered bordered cards
replaced rounded bubbles, the palette went monochrome dark grey (it started near
black and got softened once the first pass felt too high-contrast), prompt glyphs
prefix messages and chat-list rows, buttons became bracket-styled labels, and
multiple-choice prompts render as a numbered CLI menu. Amber and red stayed as
functional warning and error colors on purpose — a real terminal is monochrome
until something actually needs attention, which is what `ls`, `git diff` and a
login banner all already do.

The reasoning behind the restyle is the interesting part. The app already has the
usability an SSH session on a touchscreen can't give: a native text field with
real autocorrect and predictive text, and approval prompts that are tappable
targets instead of single keystrokes. This pass was about keeping all of that
while making it *look* like the environment it's a front end for.

Validation ran against a throwaway local mock server with headless-browser
screenshots at phone width, so the live service and its PIN gate were never
involved. That caught three real cramping bugs that would otherwise have shipped:
the header title crushed down to a single letter, a toggle's bracket wrapping
onto its own line, and the Stop/Send buttons squeezing the message field's
placeholder onto two lines.

## Per-file share links on the file server, and two self-inflicted outages

Added a Share/Unshare toggle to every file on the file server, so one specific
file can be handed to someone through a link that skips the site's PIN. A shared
link renders the same preview the owner sees — image, video, audio, PDF, markdown,
spreadsheet, 3D model, plain HTML — minus the edit and delete controls, and
anything with no in-browser preview downloads directly instead. Sharing survives a
file being moved, drops automatically if it's deleted, and switching it off kills
the old link immediately rather than leaving it quietly working.

Then it broke twice in a row, both times from that same change.

The first break came from a Python string holding a chunk of JavaScript, written
without the marker that tells Python to leave escape sequences alone. Python
turned a typed escape into a real newline before the JavaScript ever reached the
browser, which split a string literal and took down the page's entire script
block — not just the new Share button, but the whole file listing. It surfaced as
"all my files are missing," though nothing on disk had been touched; the page
simply never got past a parse error. The fix was the escaping, but the lesson was
the process: the deployed template's JavaScript now goes through a real parser
before the live service is touched, instead of being trusted by inspection.

The second break landed immediately after that fix, when every file preview
started erroring. A template-render call was still being handed a keyword argument
from an earlier draft of the change — a rename that missed one call site. Fixed
the mismatch, and this time exercised every preview route in both owner and shared
modes before calling it done, rather than trusting a syntax check on its own.

A same-day follow-up asked specifically whether HTML sharing behaves correctly.
It does, and both paths were confirmed against a real anonymous request with no
cookies rather than assumed: a plain uploaded HTML file shares by serving the raw
page, script included, exactly like the owner's own open link, while an in-site
note — itself an HTML file underneath — shares through the same framed preview it
normally gets.
