# 2026-10-03

## Ironman online: built and torn down the same day

The offline Ironman RPG was briefly turned into a persistent, .io-style multiplayer game: a shared world, bots to keep it populated, party-only boss fights, and bots wearing rare gear as a show-don't-tell loot hint. It got as far as a working game server and a rewired client that passed a two-player browser test against a throwaway server; nothing was ever deployed or exposed. The call was to tear it down because it was "shoehorning utility where it really didn't have any," and the game went back to the offline v0.7.2 build. Ironman stays a single-player offline game.

## Print server: TPU as a selectable material

Upload, multi-part plate, storefront and reslice forms gained a PLA/TPU Material dropdown, admin-only, with guests always getting PLA. Choosing TPU applies the long-standing hand-applied recipe (nozzle +5C, 90% speed through the firmware feedrate override) automatically. It is done as a post-pass over the finished gcode rather than in slicer settings, because the slicer's first-layer temperature formula would have swallowed the +5 (210/210 instead of the proven 215/210). PLA output is unchanged and TPU gcode differs in exactly four lines. Tested against scratch data only; not yet run as a real TPU print.

## The chat frontend's models were a generation behind

The model aliases looked right, but the agent SDK ships its own private copy of the CLI and spawns that one, so "sonnet/opus/fable" still resolved to the 5.0 models while the system CLI had moved on to 5.5/5.5/5.1. This was measured rather than guessed: pointing the API base URL at a throwaway local server that logged each request and returned an error showed the model field per alias. The frontend now drives the system CLI, so "are the models current" is no longer a separate thing to remember.

## A prompt-engineering playground

A new built-in entry in the chat frontend's program picker starts a clean-room chat: no instruction files, memory, tools, connectors or skills, a blank system prompt, its own empty working directory, any model. Captured requests are the proof. A normal chat sends about 27k characters of system prompt, 43k of injected context and 150 tool definitions; a playground chat sends one fixed line plus the typed message. The honest residue is that the CLI still injects the account email and a small environment block (directory, OS, model name, date), with no switch for either. The aim is to treat prompt-only experiments as real research (hypothesis, controls, repeated trials); sycophancy and calibration are the suggested first two, and none has been run yet.

Playground exchanges are recorded verbatim to a per-day file by the app, with one pointer line per chat in the daily draft. This is done app-side on purpose: telling the model it is being logged, or giving it a tool to write with, would reintroduce the contamination the playground exists to remove.

## The invisible Playground entry: two caches

The new entry was live on the server but missing on the phone. Loading the public site in a real headless browser showed the server was right all along; two caches were in the way. The browser held an old copy of the page, and the CDN was separately serving a weeks-old copy of the service worker, so the first fix (teaching the service worker to bypass the cache) never reached any device. An intermediate attempt made things worse: clearing cookies left the stale page but dropped the session, leaving an empty model list and a dead New chat button. The fixes were to serve the page shell with a revalidate-every-load header, serve the service worker uncacheable so it reloads open pages when a new version arrives, send the page to the PIN pad when the session is gone, and land logins on an address the browser cannot have stored. Two lessons: a "network-only" service worker still goes through the HTTP cache unless told otherwise, and a script file behind the CDN is cached by default unless the origin says not to. Not yet confirmed on the phone.
